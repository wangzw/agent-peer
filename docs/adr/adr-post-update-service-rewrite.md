# 更新后由新二进制重写服务定义

## 背景

服务定义包含启动 Broker 的命令与参数，格式随版本变化。执行升级的是正在运行的旧二进制，它只认识自己版本的格式，按自己的格式重写只会把旧格式写回服务定义，新版本要求的启动方式因此无法生效。

替换二进制之后必须能够确认服务定义已经是新版本要求的格式，否则更新不能算完成。更新失败时还要保留可以继续运行的旧版本，不能只换掉二进制就重启。

## 考虑过的选项

### 由正在运行的旧二进制重写服务定义

旧二进制在替换二进制之前按自己的格式重写服务定义。

**否决**：旧二进制只懂旧格式，格式变化后写回的是旧格式，新版本的启动方式不会生效。

### 由新二进制在启动时自行重写服务定义

新二进制被服务管理器拉起后，在启动流程中重写服务定义。

**否决**：Broker 的启动阶段不应修改服务定义；手工启动的 Broker 也会走到这段逻辑；启动失败发生在重写之前，`ApplyUpdate` 无法据此决定是否回滚。

### 更新后由终端命令重新执行 `service install`

替换二进制后，由发起更新的终端命令重新安装服务。

**否决**：会话内发起的升级没有终端；`ApplyUpdate` 无法确认这一步的结果，也无法在它失败时回滚。

### 旧二进制调用新二进制的固定隐藏子命令

旧二进制在换完二进制之后、重启之前，调用新二进制的一个固定隐藏子命令；由新二进制按自己的格式重写主单元并让服务管理器重新读取。

**采纳**，见决策。

## 决策

采用旧二进制调用、新二进制负责格式的分工。旧二进制在换完二进制之后、重启之前，以本服务的级别调用新二进制的隐藏子命令 `peers internal post-update --level system|user`。新二进制按自己的格式重写该级别的主单元并保留 drop-in；该子命令不启动、不重启 Broker，重启仍由 `ApplyUpdate` 的流程负责。

重新读取分两段完成。第一段在应答之前同步执行：Linux 重写后执行 `daemon-reload`；macOS 重写 plist 后启动一个脱离当前任务的辅助进程。辅助进程用 `setsid` 建立新会话，不继承调用者的标准输入输出，等 Broker 退出后先 `bootout` 再 `bootstrap`。重新读取必须等到 Broker 退出，因为 `bootout` 会停掉正在处理这条 update RPC 的 Broker，而新二进制作为它的子进程也在同一个 launchd 任务里，会一起被停掉，`bootstrap` 没有机会执行。第二段在应答之后完成：`ApplyUpdate` 应答并退出，Linux 按已重新读取的单元重启，macOS 由辅助进程重新加载。

子命令名与参数是跨版本契约，一经发布不再更改。成功时退出码为 0，失败时非零并在标准错误说明原因。第一段失败或超过时限时，`ApplyUpdate` 把二进制回滚为旧版本，不重启，向调用方报错。第二段失败时调用方已经收到成功应答，失败只写入审计与 `post-update.log`，由等待 Broker 回来的超时提示给出日志位置。新二进制不提供该子命令时，进程以 2 退出，`ApplyUpdate` 视为不需要更新后步骤而继续；这样将来删掉该子命令的版本不会让更早的更新路径卡住。

## 后果

- 从 0.4.0 起，每个版本都必须实现该隐藏子命令；命令名与参数冻结，不能改名或改参数。
- 服务定义的格式可以随版本变化，旧版本的更新路径仍能按新版本的格式完成重写。
- 每次更新多一次进程启动和一次服务管理器重新读取，两者都计入更新后步骤的时限。
- 第一段失败时整次更新失败并回滚二进制，即使新二进制本身可用。
- macOS 上先 `bootout` 再 `bootstrap` 会短暂卸载服务；`bootstrap` 失败时服务保持卸载状态，需要按 `post-update.log` 与审计记录人工处理。
- macOS 的重新读取由一个脱离 launchd 任务的辅助进程完成，它的输出写入服务日志目录中的 `post-update.log`，不影响调用方的应答。
- 具备相应权限的账户可以直接调用该隐藏子命令重写服务定义，权限与执行 `service install` 同档。

## 失效条件

服务定义的格式不再由二进制生成，或服务管理器不再提供 `daemon-reload` 与 `bootout`/`bootstrap` 的等价操作时，本决策需要重新评估。更新改由系统包管理器分发与升级时，本决策不再适用。
