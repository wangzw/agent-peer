# 以加盐摘要比对共同的 topic

## 背景

链路两端只应就双方都有成员的 [topic](../glossary.md) 交换成员名单，并且一方独有的不公开 topic 的名字不应让对方知道。默认 topic 的名字是仓库地址，容易猜到。链路的对端是用户配对过的 Broker。

## 考虑过的选项

### 交换 topic 名的明文

双方直接互报自己有成员的 topic 名，取交集。

**否决**：一方独有的不公开 topic 的名字会直接交给对方。

### 交换固定的摘要

双方互报 topic 名的摘要，摘要相同即名字相同。

**否决**：摘要不随链路变化，对端可以预先算好常见仓库地址的摘要并离线比对，也可以把在一条链路上得到的摘要拿到别的链路上重放。

### 摘要中掺入双方指纹与随机数

对“双方指纹、双方随机数与 topic 名”求摘要后交换。

**否决**：构造更复杂，而对已配对的对端没有额外的保护：对端仍然可以用猜测的名字试探。

### 交换加盐的摘要

链路建立时双方协商一个盐值，对“盐值加 topic 名”求摘要后交换。

**采纳**，见决策。

## 决策

链路两端以本次链路协商的盐值对 topic 名求摘要，交换摘要并取交集，只对交集中的 topic 交换成员名单。

## 后果

对端从摘要得不出本方独有的 topic 名。摘要只在一条链路的一次建立期间有效，不能预先计算，也不能在别的链路上重放。

**接受的代价：**

- 不防针对具体名字的试探：对端可以让自己的 Agent 加入一个猜测的名字，再看摘要是否相符，从而确认本方是否有成员在其中。对端是配对过的 Broker，topic 名不作为机密对待，因此接受这一点。
- 链路每次重建都要重新交换全部摘要和成员名单。
