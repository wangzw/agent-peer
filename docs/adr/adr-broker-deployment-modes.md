# Broker 分系统级与用户级两种部署形态

## 背景

Claude Code 把每个会话的 inbox socket 和会话注册表限定给会话所属的账户访问（[REF-claude-code-cross-session-messaging](../references.md)），普通账户下的 [Broker](../glossary.md) 因此只能为同一账户的会话投递。生产环境的常见做法是把守护进程作为系统服务运行，由管理员统一安装和维护。个人开发机上，用户希望启用工具后不经安装就能使用。一台主机上可能有多个账户各自运行会话。

## 考虑过的选项

### 只有用户级，每个账户一个

Broker 一律以普通账户运行，只服务同一账户的会话。

**否决**：多账户的主机上要逐个账户安装、配置和配对，管理员无法为整台主机统一提供一个 Broker。

### 只有系统级，全机一个

Broker 一律以特权身份作为系统服务运行，服务本机所有账户。

**否决**：安装和启动都要特权，会话的 MCP 服务进程无法在没有 Broker 时自行拉起一个，个人开发机上的用户必须先做一次系统级的安装。

### 允许同一账户运行多个实例

同一账户以不同的配置或监听地址启动多个 Broker。

**否决**：同一账户的会话无从确定归属哪个实例，同一个会话可能被登记到两个实例上，以两个身份出现在网络中，收到的消息也可能重复。

### 两种形态并存，同一账户至多一个实例

系统级 Broker 以特权身份作为系统服务运行，一台主机至多一个，服务本机上有权使用它的各个账户下的 Agent。用户级 Broker 以普通账户运行，只服务同一账户下的 Agent，一台主机上可以有多个账户各自运行一个。同一账户下至多一个实例。MCP 服务进程在没有可用的 Broker 时只拉起用户级的；系统级只由管理员安装和启动。

**采纳**，见决策。

## 决策

Broker 有系统级与用户级两种部署形态。系统级 Broker 服务本机多个账户下的 Agent，用户级 Broker 只服务同一账户下的 Agent。同一账户下至多运行一个 Broker 实例，不论它以什么配置启动。每个实例有自己的指纹、对端、名录和配置，在网络中是独立的 Broker。

## 后果

管理员可以为整台主机提供一个 Broker，个人用户不需要特权也能使用。一个账户的会话只会登记到一个实例上。

**接受的代价：**

- 两种形态在文件位置、权限判定和投递方式上不同，要分别实现和测试。
- 系统级 Broker 要以特权运行，并要读取各账户的会话注册表、向各账户的会话投递，为此要为每个被服务的账户维持一个切换到该账户的辅助进程，这些操作都由它以该账户的身份执行。
- 非特权账户的账户锁放在 `/tmp` 下以该账户命名的目录里，其他本机账户可以抢先建立这个目录，使该账户的用户级 Broker 拒绝启动。
- 系统级 Broker 把多个账户的 Agent 放在同一个 Broker 之下：不同账户的 Agent 只要同在一个 topic 就互相可见，它们共用一个指纹、一份对端和一个别名。
- 同一台主机上的多个 Broker 在网络中互不相干，各自配对；另一台主机要与这台主机上的两个账户通信，可能要配对两次。
- 一个账户同时有系统级和用户级的 Broker 可用时，MCP 服务进程要按固定的顺序选定其一，用户需要知道自己的会话登记在哪一个上。
- 实例的唯一性要按账户和主机判定，不能依赖家目录下的文件，因为家目录可能由多台主机共享。
