agent-peer 把互不认识的 Broker 连在一起，每条投递出去的消息最终都进入一个 Claude Code 会话，而来自其他主机的文本应视为不可信输入。本页说明信任从哪里来、每种机制保护什么，以及保护到哪里为止。

## 配对与指纹

每个 Broker 使用自签名证书，身份是公钥的指纹，没有证书颁发机构为它签名。链路使用 TLS 1.3，双方各自核对对方的指纹。

两个 Broker 只在完成配对之后才互相信任。接受方生成一次性配对密钥，连同对外地址一起展示；用户通过系统之外的途径把这两样交给另一方。传递一次性密钥的途径必须可信。一次性密钥有 16 个字符，限时有效，只能使用一次。另一种是预置静态密钥，由用户或管理员写进 Broker 的配置文件：16 至 128 个字符，可以重复使用，不会过期，系统不会生成它。握手证明双方都持有这个密钥，并把它与各自看到的指纹绑定。此后 Broker 只凭保存下来的指纹认对端。

别名和对外地址不参与认证。别名只用于显示，地址说明连到哪里，不说明对面是谁。配对逐对建立，不能传递：A 与 B 配对、B 与 C 配对，不代表 A 与 C 互相信任。要不再信任一台主机，得在每个与它配对过的 Broker 上分别解除配对。已配对的 Broker 报告的自己名下 Agent 与 topic，本机无法核实。

静态密钥以明文保存在配置文件里。能读这个文件的账户就能读到密钥，并在没有写权限的情况下用它让本 Broker 增加对端。密钥的随机性由设置它的人负责，长度下限挡不住够长而好猜的密钥。发起方在核实对方之前就发出由密钥算出的查找标记，所以能截获握手的一方，以及发起方因地址写错或域名被劫持而连到的任何一方，都可以据此离线穷举弱密钥。用这个密钥配对过的主机都知道它；这样的主机若能截获或误导新主机的连接，就能冒充接受方。更换密钥后，再用旧密钥配对会被拒绝；已经凭它配对的对端仍然保持配对，要逐个解除。

## 默认不公开

Broker 被用户设为公开之后，才会发布写着指纹、别名和对外地址的名片。不公开的 Broker 照常接收其他 Broker 的名片，它的对端也不会把它的信息继续传出去。不公开的 Broker 还不能声明公开 topic：声明要签名，而签名会带出它的指纹。

不公开不等于隐藏。对端知道它的指纹和别名，主动与它配对的主机会知道它的对外地址，能连到监听端口的主机都能看到它的证书。

## topic 决定可见范围

两个 Agent 至少同在一个 topic 时，才能互相看见、互发消息。同一台主机上的两个会话和不同主机上的会话适用同一条规则；跨主机时，链路两端各自检查。

加入 topic 只需要知道名字。没有管理员、邀请和审批，成员也不能被移出。所以 topic 的名字不是秘密：谁知道了都能加入，一个 topic 里的 Agent，对所有在该 topic 有成员的已连接对端都可见。要发给 topic 里的全部成员，得逐个调用。

会话会加入项目配置文件声明的默认 topic。没有这个文件时，默认 topic 取自工作区 git 仓库的 `origin` 地址。可以关闭自动加入。

## 管理操作以配置文件权限为准

Broker 根据操作系统为本机 socket 另一端进程提供的凭据判断调用方能做什么，不采信调用方自己说了什么。写权限允许修改配置、生成一次性配对密钥、配对和解除配对；读权限允许读取配置、读取审计日志，以及查看调用方自己名下以外的状态。列出 Agent 和 topic、加入与退出 topic、发送消息，都不需要文件权限。

因此系统级 Broker 可以用普通的文件权限委派管理：把写权限授予某个组，组里的账户就能经工具管理 Broker。这也意味着识别出的是账户，不是人，也不是模型。账户下的每个进程都以该账户的权限行事，受提示注入操纵的模型发起的调用，与用户本人发起的调用无法区分。

## 投递消息时不使用认证令牌

Claude Code 允许向会话 inbox socket 写入的进程出示认证令牌。agent-peer 不出示令牌，也不读取令牌文件。于是投递的文本进入目标会话时，被当作没有声明权限类别的发送方。接收方会话对这类消息执行入站控制。以跳过权限确认的模式运行且没有设置入站策略的会话，会把每条消息暂扣，逐条批准后才放进会话。以无界面方式运行且跳过权限确认的会话收不到 agent-peer 的消息：接收方的 Claude Code 先把消息暂扣，随后因发送方没有声明权限类别而丢弃，而发送方那边已经返回成功。见[设计取舍与注意事项]({{< relref "limitations.md" >}})。

Broker 的设计是不做任何会话的后代进程。用户级 Broker 由服务管理器启动，或由用户在终端里启动，不在会话的进程树内；系统级 Broker 则作为服务运行在进程树之外。能使用本机系统级 Broker 的账户不需要用户级 Broker；正在运行的用户级 Broker 优先于系统级 Broker，除非会话的工具配置指定了某个 Broker。

原生 Windows 不支持，因为那里的 inbox 连接强制要求认证行。

## 限速与循环检测交给 Claude Code

agent-peer 不限制发送频率，不携带跳数，也不检测消息循环。接收端的 Claude Code 自己有一套规则。它按帧里的回复地址识别发送方，没有回复地址时按写入进程识别。每个发送方一个令牌桶，容量 30，每秒补充 0.5 个；同一发送方在 30 秒内发来与上一条内容完全相同的消息时，后一条被丢弃；未处理的会话间消息至多排队 50 条。

agent-peer 写入时不带回复地址，所以经同一个用户级 Broker，或经系统级 Broker 的同一个账户辅助进程写入的全部消息，不论来自哪个 Agent，都算同一个发送方，共用一个令牌桶。Claude Code 自带的循环检测依赖消息里记录的经过路径，agent-peer 的消息没有这项记录，因此两个 Agent 之间的循环只能靠接收端的限速约束。Claude Code 可以改动上述限速与去重数值，也可以远程调整它们。见[设计取舍与注意事项]({{< relref "limitations.md" >}})。

## 操作系统账户是隔离边界

用户级 Broker 只服务本账户，拒绝其他账户的调用。系统级 Broker 服务获准使用它的账户，并且只接受调用方账户所拥有的 inbox socket 的登记。同一个账户内部不再有进一步的隔离。
