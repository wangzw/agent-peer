agent-peer connects Brokers that do not know each other, and every delivered message ends up inside a Claude Code session, where text from another host should be treated as untrusted input. This page describes where trust comes from, what each mechanism protects, and where protection stops.

## Pairing and fingerprints

Each Broker has a self-signed certificate, and its identity is the fingerprint of its public key. No certificate authority signs it. Links use TLS 1.3, and each side checks the other's fingerprint.

Two Brokers trust each other only after a pairing. The accepting side creates a one-time pairing key and shows it together with its advertised addresses; the user passes both to the other side through a channel outside the system. The channel that carries a one-time key must be trusted. A one-time key is 16 characters, expires, and works once. The alternative is a pre-provisioned static key that the user or administrator writes into the Broker's configuration file: 16 to 128 characters, reusable, never expiring, and never generated by the system. The handshake proves that each side holds the key and binds it to the fingerprints each side observed. After that, a Broker recognizes its peer by the saved fingerprint alone.

The alias and the advertised addresses are not authenticated. An alias is for display, and an address says where to connect, not who answers. A user Broker's default alias contains the name of the account that runs it, which peers and anyone who receives a public broker card can see; set `broker.alias` to keep the account name out of the agent address. Pairing is pairwise and not transitive: if A pairs with B and B pairs with C, A and C do not trust each other. To stop trusting a host, unpair it on every Broker that paired with it. A paired Broker's reports about its own agents and topics cannot be verified from this side.

A static key is stored in plaintext in the configuration file. Any account that can read the file can read the key and use it to make this Broker add a peer, even without write permission. The person who sets the key is responsible for its randomness; the length check does not stop a long but guessable key. Before the accepting side is verified, the initiating side sends a lookup marker derived from the key, so anyone who captures the handshake, or any host the initiator reaches through a wrong address or a hijacked domain name, can use it to brute-force a weak key offline. A host that has paired with this key knows it; if it can intercept or mislead a new host's connection, it can impersonate the accepting side. Replacing the key blocks new pairings made with the old one; peers already paired with it stay paired until they are removed individually.

## Private by default

A Broker publishes a broker card with its fingerprint, alias, and advertised addresses only after the user sets it public. A private Broker still receives broker cards from other Brokers, and its peers do not pass its information on. A private Broker also cannot declare a public topic, because the declaration has to be signed and the signature reveals the fingerprint.

Private does not mean hidden. A peer knows the fingerprint and alias, a host that initiates pairing learns the advertised addresses, and any host that can reach the listening port can see the certificate.

## Topics decide visibility

Two agents can see each other and exchange messages only when they share at least one topic. The same rule applies to two sessions on one host and to sessions on different hosts, and for a remote agent both ends of the link check it.

Joining a topic needs only the name. There is no administrator, invitation, or approval, and a member cannot be removed. A topic name is therefore not a secret: anyone who knows it can join, and everyone in the topic is visible to every connected peer that has a member in it. Sending to all members of a topic takes one call per recipient.

A session joins a default topic declared by its project configuration file. Without that file, the default topic comes from the workspace's git origin address. Automatic joining can be turned off.

## Management operations need configuration file permission

The Broker decides what a caller may manage from the operating system's process credentials for the local socket, not from what the caller says. Write permission on the Broker's configuration file allows changing the configuration, creating a one-time pairing key, pairing, and unpairing. Read permission allows reading the configuration, reading the audit log, and seeing status beyond the caller's own agents. Listing agents and topics, joining and leaving topics, and sending a message need neither.

This means a system Broker can delegate management with ordinary file permissions: grant write access to a group and its accounts can manage the Broker through the tools or the terminal commands. An administrator running the terminal commands with `sudo` is checked as root, so the default 0600 file already lets root manage the Broker. It also means the account, not the person or the model, is identified. Every process under an account acts with that account's authority, and a call made by a model steered by prompt injection is indistinguishable from one the user intended.

## Messages enter a session without an authentication token

Claude Code lets a process that writes to a session's inbox socket present an authentication token. agent-peer does not present it and does not read the token file. Delivered text therefore enters the target session as a sender with no declared permission category. The receiving session applies its inbound controls to such a message. A session that skips permission prompts and has no inbound policy set holds each message for individual approval. A session that runs headless and also skips permission prompts cannot receive messages from agent-peer: the message is held and then dropped because the sender declares no permission category, while the sending side has already returned success. See [design choices and caveats]({{< relref "limitations.md" >}}).

The Broker is designed not to be a descendant of any session. A user Broker is started by the service manager or by the user in a terminal, outside the session's process tree, and a system Broker runs as a service outside it. An account that can use the host's system Broker needs no user Broker, and a running user Broker takes precedence over the system Broker, unless the session's tool configuration names a Broker.

Native Windows is not supported because inbox connections there require the authentication line.

## Rate limits, loop detection and duplicate suppression

agent-peer does not rate-limit sending, count hops, or detect message loops. The receiving Claude Code applies its own rules. It identifies a sender by the reply address in the frame, or by the writing process when there is none. Each sender gets a token bucket with capacity 30 that refills at 0.5 per second, and at most 50 pending cross-session messages are held. The 30-second rule is separate: it drops a message from the same agent to the same session whose content repeats the previous one. The signature is part of that content, so the rule distinguishes agents even when they share one token bucket; two agents do not suppress each other's messages.

The receiving Broker also drops a copy that a retry within one send produces. It identifies the copy by the message identifier in the delivery request and keeps the result in an in-memory table for `send.dedupe_window`, 5 minutes by default. The table is lost on restart, so if the Broker restarts between two retries, the same message can be written twice. A send made after the outcome is unknown carries a new identifier and is not deduplicated.

agent-peer writes without a reply address, so everything written through one user Broker, or through one account helper of a system Broker, counts as one sender and shares one token bucket, whichever agent sent it. Claude Code's own loop detection relies on a path recorded in its messages; agent-peer messages carry no such record, so the rate limit is the only thing that constrains a loop between two agents. Claude Code can change its rate limits and its 30-second rule, and it can adjust them remotely. See [design choices and caveats]({{< relref "limitations.md" >}}).

## The operating-system account is the isolation boundary

A user Broker serves only its own account and rejects calls from other accounts. A system Broker serves the accounts allowed to use it, and accepts a registration only for an inbox socket owned by the calling account. Within one account there is no further separation.
